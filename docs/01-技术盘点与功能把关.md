## 一、这个 AI 版到底是什么

一个**单仓库全栈单体**，共 5 个模块：

| 模块 | 位置 | 规模 |
|---|---|---|
| 后端 | `todolist-src/backend` | 30 个 Java 文件，约 1200 行 |
| 前端 | `todolist-src/frontend` | 3 个页面 + 2 个 api 文件，约 1100 行 |
| 构建产物 | `todolist-build` / `todolist-deploy` | jar + tar.gz |
| 前端打包副本 | `frontend-package` | 前端 build 后的静态文件 |
| 杂项 | `chrome-*` / `edge-*` | 与项目无关，可忽略 |

跑起来的方式：前端 `vite build` → 产物拷进后端 `src/main/resources/static` → `java -jar` 一个进程同时提供页面和接口。

## 三、前端技术栈（你不用精通，但必须懂 3 件事）

Vue 3.5（`<script setup>`）+ Vite 5 + Element Plus 2.8 + axios 1.7 + vue-router 4（history 模式，`base: '/todolist/'`）。

你必须懂的 3 件事，否则联调必崩：

1. **请求怎么发**：`axios.create({ baseURL: '/api' })`，所有接口都拼在 `/api` 下。
2. **token 怎么带**：请求拦截器从 `localStorage` 取 token，塞 `Authorization: Bearer xxx`。
3. **响应怎么解包**：后端返回 `{code,msg,data}`，响应拦截器判断 `code!==200` 就弹错，`==200` 才把整个 res 往下传——所以页面里拿数据是 `res.data`，不是 `res.data.data`。

## 四、与苍穹外卖横向对比

| 维度 | 苍穹外卖 | AI 版 | 差异意味着什么 |
|---|---|---|---|
| 工程结构 | 多模块（common / pojo / server） | 单模块 | AI 版更简单，新手不会迷路 |
| 持久层 | MyBatis **XML** + 动态 SQL | MyBatis **注解** | XML 才能练 `<if>`；注解更短但复杂 SQL 会难看 |
| 分页 | PageHelper 一行搞定 | 没有，全量返回 | 任务量小时不分页也够 |
| 缓存 | Redis | 无 | 砍掉，少一个故障点 |
| 登录态 | JWT + 拦截器 + `ThreadLocal(BaseContext)` | JWT + 拦截器 + `@RequestAttribute` | 少了 ThreadLocal，用 request attribute 替代，效果一样 |
| 密码 | MD5 | BCrypt | BCrypt 更安全，但 API 不同（`encode`/`matches`） |
| 接口文档 | Swagger / Knife4j | 无 | 要演示体面就补 springdoc，30 分钟 |
| 公共字段填充 | AOP + `@AutoFill` | 手动 `setCreatedAt(LocalDateTime.now())` | AOP 是很好讲的亮点，补回来成本低 |
| 文件上传 | 阿里云 OSS | 无 | 不需要 |
| 消息推送 | WebSocket | 无 | 你的"弹窗提醒"用不上它（见 02 文档） |
| 部署 | Nginx + jar | 内嵌 Tomcat 单 jar | AI 版更省事 |
| 前端 | 微信小程序 | Vue3 SPA | 完全不同，但那是同伴的活 |

**三句话总结：**

1. 主干（三层架构 + JWT + 统一响应 + MyBatis + 全局异常）**一模一样**，你学的东西直接能用。
2. 它漏掉的恰好是苍穹外卖的"可讲点"：ThreadLocal、AOP 自动填充、Swagger、PageHelper、MyBatis XML。**补回来成本很低，讲起来很值。**
3. 它多出来的只有两样值得学：Spring Boot 3 的 `jakarta` 差异、SPA 打包进后端。

## 六、5 个改进功能：技术把关

### 总览

| # | 功能 | 需要的新技术 | 掌握度 | 工时 | 归属 | 优先级 |
|---|---|---|---|---|---|---|
| 5 | 截止时间精确到分 | `LocalDateTime` + `@JsonFormat` | **95%** | 1.5h | 后端+前端 | **P0** |
| 1 | 过期置顶标红 | SQL 排序 + CSS | **100%** | 1.5h | 后端+前端 | **P1** |
| 3 | 到期弹窗提醒 | `setInterval` + `ElNotification` | **80%**（纯前端） | 2.5h | 前端 | **P1** |
| 4 | 每日固定任务 | 数据模型设计 | **70%** | 3h | 后端 | **P2** |
| 2 | 下拉刷新 | touch 事件 | **60%**（纯前端） | 0.5h | 前端 | **P3** |

### 关键认知：5、1、3 是同一根链条

```
时间精度（5）→ 时间比较（1）→ 时间触发的反馈（3）
```

**5 不做，1 和 3 都是残废**：只精确到天，你没法判断"今天 18:00 的任务现在 19:00 该提醒了"。
所以 5 必须第一个做，而且要**在建表阶段就做**——表建错，后面每一层返工。

### 逐个拆解

#### 5. 截止日期精确到分 → 掌握度 95%

**需要的技术，全在你已学范围：**

| 技术 | 你会不会 | 在哪学的 |
|---|---|---|
| MySQL `DATETIME` | ✅ | 苍穹外卖订单表 |
| Java `LocalDateTime` | ✅ | 苍穹外卖 `Order` 实体 |
| Jackson 序列化日期 | ⚠️ 半会 | 需要 `@JsonFormat` 注解 |
| MyBatis 类型映射 | ✅ | 3.5+ 自动支持 LocalDateTime，不用 TypeHandler |
| 前端 `el-date-picker type="datetime"` | 同伴的活 | — |

**要改 7 处，漏一处就报错：**

1. `schema.sql`：`due_date DATE` → `due_time DATETIME`
2. `entity/Todo.java`：`LocalDate dueDate` → `LocalDateTime dueTime`
3. `dto/TodoRequest.java`：同上 + `@JsonFormat`
4. `mapper/TodoMapper.java`：SQL 列名
5. `service/impl/TodoServiceImpl.java`：赋值逻辑
6. `application.yml`：`spring.jackson.time-zone`
7. 前端：`el-date-picker`、列表展示、`isOverdue()` 判断

**两个必踩的坑：**

- Jackson 默认把 `LocalDateTime` 序列化成数组 `[2026,11,14,18,30]`，前端拿到直接懵。必须 `@JsonFormat(pattern="yyyy-MM-dd HH:mm")`。
- 前端的 `value-format` 必须和后端的 `pattern` **一字不差**，否则传过去解析失败。

#### 1. 过期置顶标红 → 掌握度 100%

**AI 版其实已经做了一半**：`TodoView.vue` 里有 `isOverdue(todo)` 和 `.due.overdue` 的红色样式。
但它只精确到天，而且**排序没考虑截止时间**。

要补的：

- 后端 SQL：`ORDER BY completed ASC, (due_time < NOW() AND completed = 0) DESC, priority DESC, due_time ASC`
- 前端：加"已逾期"分组标题 + "已逾期 3 天"文案

**技术全是学过的**：SQL 表达式、`LocalDateTime` 比较、CSS class 绑定。没有新东西。

#### 3. 到期弹窗提醒 → 掌握度 80%，但**这是前端功能**

**最重要的认知纠正：这不是后端功能。** 你不需要 `@Scheduled`，不需要 WebSocket，不需要写任何 Java 代码。

三种实现，只看第一种：

| 方案 | 技术 | 工时 | 评价 |
|---|---|---|---|
| **A. 前端轮询**（推荐） | `setInterval` + `ElNotification` + `localStorage` 去重 | 2h | 页面开着就有效，演示足够 |
| B. 浏览器通知 | `Notification API` + 权限申请 | +1h | 需 localhost/https，加分 |
| C. 后端推送 | `@Scheduled` + WebSocket/SSE | 8h+ | **两天半做必翻车，别碰** |

A 的要点（交给同伴）：

- 每 30 秒扫一次未完成任务
- 条件：`due_time <= now && !completed`
- `ElNotification({ title: '任务到期', message: todo.title, type: 'warning', duration: 0 })`
- **必须去重**：用 `Set` + `localStorage` 记录已提醒的 `todoId`，否则每 30 秒弹一次
- 页面刷新后从 `localStorage` 恢复已提醒列表

**坑**：关掉浏览器就失效，这是浏览器限制不是 bug。演示时主动说一句"真实产品会用 WebSocket 或系统通知"，反而显得你懂。

#### 4. 每日固定任务 → 掌握度 70%，是唯一需要"设计"的

技术本身你都会（建表、SQL 日期函数、Service 分支），难的是**选模型**。

| 方案 | 数据模型 | 工时 | 适用 |
|---|---|---|---|
| **A. 打点式**（推荐） | `todo` 加 `is_daily` + `last_done_date` | 3h | 只需"今天完成没有" |
| B. 实例式 | 新增 `todo_instance(todo_id, date, completed)` | 5h | 要历史打卡、连续天数 |
| C. 定时生成 | `@Scheduled` 每天 0 点 insert | 4h+ | **不推荐**，多一个故障点 |

A 的核心逻辑只有三条：

1. 建任务时勾"每日"→ `is_daily = 1`
2. 查询时用 SQL 算状态：`completed = (last_done_date = CURDATE())`
3. 勾选时：`UPDATE todo SET last_done_date = CASE WHEN last_done_date = CURDATE() THEN NULL ELSE CURDATE() END`

不需要定时任务，不需要新表，不需要"每天生成"。

**坑**：
- 服务器时区：`application.yml` 的 JDBC URL 必须带 `serverTimezone=Asia/Shanghai`，否则 `CURDATE()` 会差 8 小时
- "每日任务"和"今天到期的任务"是两拨数据，列表视图要合并 + 去重

#### 2. 下拉刷新 → 掌握度 60%，P3

**现实问题**：PC 浏览器用鼠标拖不出"下拉"手势，课堂演示时基本看不出效果。

| 做法 | 代码量 | PC 效果 |
|---|---|---|
| 真·手势（touch 事件） | ~80 行 | 无效 |
| 刷新按钮 | 3 行 | ✅ 有效 |
| 定时自动刷新 | 10 行 | ✅ 有效（配合功能 3 一起做） |

**建议**：先做"按钮 + 定时刷新"，真手势留到最后有余力再说。半天时间不值当。
