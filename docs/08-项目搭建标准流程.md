# 08 · Java Web 后端项目搭建标准流程

> 这份文档回答三个问题：**做什么、在干嘛、为什么这么做**。
> 对象：已经会写 CRUD，但不知道「一个正经项目从零到能交付」该按什么顺序走的人。
> 说明：本文写的是**行业通行做法**，不是本项目已有的历史路径。两者不一致时以本文为准，项目逐步对齐。

---

## 先说结论：资深和中级的差别不在用多少技术

| | 中级 | 资深 |
|---|---|---|
| 动手前 | 打开 IDEA 就开始建项目 | 先定 3 个「以后改起来最贵」的决策 |
| 依赖 | 需要什么加什么 | 只加当下用得到的，并知道加上去的副作用 |
| 骨架 | 先写业务，异常后面再说 | 横切设施全部在**第一个业务接口之前**落地 |
| 验证 | 能跑 demo 就行 | 每一步留可复现的证据（命令 + 预期输出） |
| 交付 | 我机器上能跑 | 换台机器一条命令能起 |
| 留缝 | 全写死 | 配置外置、脚本入版本库、迁移工具兜底 |

后面的每一步，都对应这张表里的某一行。

---

## 第 0 步：动手前的三个决策

这一步不写代码，但决定了后面 90% 的返工量。

### 0.1 锁定版本（最贵、最不可逆）

**做什么**：确定 Spring Boot 父版本、JDK 版本、数据库版本，写进一份文档，之后不再改。

**在干嘛**：Spring Boot 的 `<parent>` 是一个 BOM（Bill of Materials，物料清单），它管住了几百个依赖的版本。你选了 `2.7.18`，那么 Jackson、Tomcat、HikariCP、日志库的版本全部被它钉死，你不用也不该手写。

**为什么不能随意改**：Boot 2.x → 3.x 的迁移里，`javax.*` 全部变成 `jakarta.*`，涉及 Servlet、Validation、JPA 三个包，一个项目里几百处 import。这是**不可逆决策**，必须在第一行代码前定死。

**怎么判断**：看三件事——团队会不会维护、教程/资料是否匹配、第三方库（MyBatis、PageHelper、Swagger）是否已支持该大版本。三个都满足才动。

### 0.2 定包结构

**做什么**：决定按「技术分层」还是「业务领域」分包。

| 方式 | 长什么样 | 适合 |
|---|---|---|
| 技术分层 | `controller/` `service/` `mapper/` `entity/` | 模块少、人少、教学项目 |
| 领域分包 | `todo/` `user/` `tag/`，每个域内部再分层 | 模块多、多人并行、长期维护 |

**为什么重要**：包结构是「谁和谁能互相引用」的物理边界。改包结构会让 git blame 全部失效、code review 地狱。小项目用技术分层就够，但要知道这是一种**取舍**，不是真理。

### 0.3 定交付形态

**做什么**：打包成 `jar` 还是 `war`。

**为什么**：`jar` = 内嵌 Tomcat，`java -jar` 就能起，运维简单，云原生默认；`war` = 丢进外部 Tomcat，适合公司已有统一容器。选错的话，部署脚本、CI 配置、健康检查全要重做。

**结论**：除非公司强制，一律 `jar`。

## 第 1 步：生成骨架（5 分钟）

### 做什么

用 Spring Initializr（`start.spring.io` 或 IDEA 内置）生成，而不是手写 `pom.xml`。

填四项：Project = Maven｜Language = Java｜Spring Boot = 第 0 步定的版本｜Java = JDK 版本。
命名：Group = `com.公司.项目`，Artifact = 小写中划线，如 `todolist`。

### 在干嘛

工具在替你完成三件固定的事：写 `pom.xml`、建 `src/main/java` 与 `src/main/resources` 目录、生成启动类和一个测试类。这三件事没有判断空间，手写只是浪费时间和制造 typo。

### 为什么只勾当下需要的依赖

Initializr 的依赖列表是一个「陷阱菜单」：勾了 `Spring Security`，它默认把所有请求拦成 401；勾了 JDBC 相关却不配数据源，启动直接失败。

**每勾一个依赖 = 改变应用的启动行为**，不是「多几个 jar 而已」。

### 验收

```powershell
mvn -B clean package
```

跑成功、`target/` 下出现 jar。**这一步的红线是：零改动就能构建成功。** 如果这里就报错，说明网络/镜像/JDK 不匹配，别急着写业务。

---

## 第 2 步：第一次提交（10 分钟）

### 做什么

`git init` → 写 `.gitignore`（至少要含 `target/`、`.idea/`、`*.iml`、本地配置文件）→ 提交一次，message 写 `chore: 初始化工程骨架`。

### 在干嘛

把「工具生成的代码」和「人写的代码」在历史里分开。以后出问题，你能一眼看出哪次提交是骨架、哪次是业务。

### 为什么

新手最常见的 git 事故是：`target/` 被提交，某次构建后几百个 class 文件进入版本库，仓库从 2MB 变成 300MB，再也清不掉。

---

## 第 3 步：配置分层（半天）

### 做什么

- `application.yml` 只放**所有环境都一样**的东西（应用名、编码、时区）
- `application-dev.yml` / `application-prod.yml` 放环境相关的（数据源、Redis 地址、日志级别）
- 用 `spring.profiles.active` 切换
- 密码不进 git：用环境变量占位 `${DB_PASSWORD}`

### 在干嘛

把「代码」和「部署时的值」拆开。同一个 jar，靠外部配置跑在不同环境。

### 为什么

如果数据库密码写进 yml 并提交，第一次要上生产时你会发现：开发库密码和生产库密码不一样，而代码是同一份。要么改代码重新打包，要么在服务器上手动改 jar 里的文件——这两种都是事故。

**判断标准**：同一个 jar，不重新打包，只换环境变量，能在开发机和服务器上分别启动。

## 第 4 步：横切基础设施（1–2 天，骨架的真正内容）

「横切」= 每个接口都要用、但和具体业务无关的东西。**必须在第一个业务接口之前做完**，否则写 30 个接口后再补，等于 30 次返工。

按这个顺序做，每一步都依赖上一步：

### 4.1 统一响应体

所有接口返回同一个外壳：`{ code, msg, data }`。

**为什么**：不统一的话，前端要为每个接口写一套解析；出错时前端无法判断是「参数错」还是「服务器炸」。

### 4.2 错误码集中管理

把所有 `code` 放进一个枚举或常量类，不要散落在各个 `throw` 里。

**为什么**：前端和后端要对着同一张码表联调。码散在代码里，就会出现「同一个错误在两个接口返回不同码」。

### 4.3 全局异常处理

`@RestControllerAdvice` + 若干 `@ExceptionHandler`。

**为什么**：不加的话，异常走默认错误页，前端收到 HTML，状态码永远 500，Controller 里到处 try-catch。

### 4.4 参数校验

`@Valid` + `@NotBlank` / `@Size` 等注解，校验失败由 4.3 统一转成 400。

**为什么**：把「用户输入合法性」从业务逻辑里剥出来。手写 if 判断既啰嗦又容易漏。

### 4.5 跨域配置

前后端分离开发时，前端 `localhost:5173` 调后端 `localhost:8080` 属于跨域，浏览器会拦。

**为什么现在做**：等前端第一次联调才发现，会误以为是接口写错了，浪费半天。

### 4.6 日志规范

统一用 `@Slf4j`，禁止 `System.out.println`；日志里**不打密码和 token**。

**为什么**：线上排查全靠日志。日志格式不一致，grep 都 grep 不出来。

### 4.7 健康检查接口

`GET /api/health` 返回 `{code:200, data:{status:"UP"}}`。

**为什么**：部署后要能一眼确认「进程活着且能处理 HTTP」，而不是翻日志猜。

## 第 5 步：数据层

### 5.1 建表脚本进版本库

`backend/sql/schema.sql`，和代码一起提交。

**为什么**：数据库结构是项目的一部分。只存在某个人的 Navicat 里，换台机器就重建不出来。

### 5.2 连接池参数要显式配置

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      connection-timeout: 3000
```

**为什么默认值不一定对**：默认最大连接数是 10，但如果你的数据库只允许 20 个连接，而部署了 3 个实例，就是 30 个连接抢 20 个名额，会随机超时。**连接数是「应用实例数 × 池大小 ≤ 数据库上限」**，这个算式必须在部署前算一遍。

### 5.3 生产环境用迁移工具

Flyway 或 Liquibase，脚本编号管理，而不是手动执行 SQL。

**为什么**：手工会漏、会重、会顺序错。生产环境改表出事，多半是因为「谁在什么时候执行了哪条 SQL」没人说得清。

### 5.4 ORM 选型要看 SQL 可控性

MyBatis（SQL 手写、可控）vs MyBatis-Plus（单表省事）vs JPA（对象优先、复杂查询难控）。

**判断依据**：查询里有没有大量多表关联和动态条件。有 → MyBatis；纯单表 CRUD → Plus/JPA 更省。

---

## 第 6 步：骨架验收（写死标准，不通过不许写业务）

五条，缺一不可：

1. `GET /api/health` → 200，符合统一格式
2. 不存在的路径 → 404（不是 500、不是白页）
3. 故意 `throw new RuntimeException()` → 500 + 统一格式（响应体里**没有堆栈**）
4. `@NotBlank` 字段传空 → 400 + 业务码
5. `mvn test` 全绿

**为什么要有这份清单**：这五条覆盖了「路由、序列化、异常、校验、构建」五个维度。全部通过，说明骨架的每条通道都通了；后面写业务时出的错，就一定是业务逻辑的错，不用再怀疑框架。

---

## 第 7 步：协作设施（半天）

- **README 只写三件事**：怎么启动、怎么跑测试、环境变量有哪些。不写架构长文。
- **commit message**：`feat:` / `fix:` / `refactor:` / `chore:` 前缀 + 一句话说清「改了什么、为什么」。
- **分支模型**：2–3 人团队用 trunk-based（主干开发 + 短分支），别上 GitFlow，那是给有发布窗口的团队用的。
- **CI**：一个 GitHub Actions 跑 `mvn -B verify`。**这是唯一能保证「别人拉下来确实能构建」的手段。**

---

## 第 8 步：打包与部署前置

```powershell
mvn -B clean package -DskipTests
java -jar target/todolist-1.0.0.jar --spring.profiles.active=prod
```

要提前确认的三件事：

1. **jar 里有没有把配置打进去**（打进去了就没法用外部配置覆盖）
2. **端口能不能改**（`--server.port=9090` 必须生效）
3. **日志能不能落盘**（容器里只看得到 stdout，出问题就没证据了）

**判断标准**：把 jar 拷到另一台机器，只给 JDK，一条命令能起来。

## 附：新手最常见的 7 个错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 先写业务再补异常处理 | 30 个接口返工 | 骨架验收清单先过 |
| 依赖一次勾满 | 启动失败，且不知道是谁导致的 | 用到才勾 |
| 密码写进 yml 并提交 | 换环境就要改代码 | 环境变量占位 |
| `target/` 提交进 git | 仓库膨胀，无法回滚 | 第一条就写 `.gitignore` |
| 连接池用默认值 | 生产随机超时 | 按「实例数 × 池大小」算 |
| 用 `System.out` 打日志 | 线上查不到、没法分级 | 统一 `@Slf4j` |
| 没有健康检查 | 部署后靠猜 | `/api/health` |

---

## 一句话总结

**资深程序员的搭建流程，本质是「把不可逆的决策提前、把横切的成本前置、把每一步变成可验证的证据」。** 技术选型只是其中最小的一块。
